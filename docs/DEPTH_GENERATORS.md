# Depth generator selection and candidates

Research checked 27 September 2026. The shipped choice is **Automatic (recommended)**, which resolves to the established Depth Anything V2 Small adapter in both editions. An advanced control also allows an explicit V2 choice. These two selections use the same model and output; V3 and Depth Pro are research candidates, not functioning choices yet.

[Current browser ONNX model](https://huggingface.co/onnx-community/depth-anything-v2-small) documents a Transformers.js depth-estimation pipeline. | Already running through the browser's WebGPU/CPU fallback and the local Python model; the hosted container has no PyTorch. | Keep as Automatic and as the explicit, verified choice. |

The official checkpoint is about 137 MB. | An [ONNX Community export](https://huggingface.co/onnx-community/depth-anything-v3-small/tree/main) is about 105 MB including external weights, but presently has a bare `config.json` and no image processor configuration or usage instructions. ## Contract for an additional adapter

1. The front end's `depthGenerators.ts` lists only verified adapters. `automatic` resolves to the recommended identifier; it is not a model. Each runtime explicitly advertises what it can run. The Studio and View-Master controls use the same catalog. The existing V2 browser adapter remains pinned and keeps its retry and WebGPU-to-CPU fallback.
2. An adapter takes the original image and returns a depth map aligned to it, finite and normalized to **0–1, with higher values nearer**. V2's relative disparity already follows that convention. A metric-distance model such as Depth Pro needs an explicit, tested distance-to-nearness conversion before it reaches stereo rendering; metre values and estimated camera intrinsics should be retained separately if ever needed, not mistaken for a measured viewer or printer dimension. Check V3's convention empirically as part of its adapter.
3. The hosted edition runs each optional model in the browser. No model weights, PyTorch, or large inference dependencies enter `backend/requirements-hosted.txt` or the production Docker image. A browser adapter must handle its own model download, preprocessing, output conversion, device fallback, and user-facing failure stage. Do not infer usability from the existence of an ONNX file alone.
4. The local backend currently validates `GET /depth-map?generator=automatic|depth-anything-v2-small` and preserves calls without the parameter. Before a second local generator is registered, key the session's AI-depth cache by source **and generator**, route the selected identifier to its adapter, and invalidate active stereo/depth-edit caches only when a new depth map is actually produced. The current `depth_map_ai.npy` is a single V2 cache, so simply switching a model name in the endpoint would silently reuse old depth.
5. Keep the advanced chooser collapsed. A choice affects the next source image or the next View-Master build, not an already generated depth map. Avoid an automatic regeneration on changing the choice. Preserve imported depth and stereo-pair workflows.

## Gates before exposing another choice

- Verify checkpoint provenance and exact license; record the version, weight size, and separate optional download path.
- Compare V2 and the candidate on the **same images**, including a nearby object, distant background, thin edges, sky, and a non-photographic image. Confirm near/far orientation, alignment, uniform-depth handling, NaNs, and the actual stereo output, not just that inference returns an array.
- Exercise the browser adapter on WebGPU and the fallback browser CPU path with the project’s supported devices. Check first download, warm cache, memory use, retry/error reporting, and that the hosted container stays lightweight.
- For a local-only adapter, test startup, inference, and memory on the intended local hardware. The 1.9 GB Depth Pro checkpoint alone does not establish usable Mac performance.
- Extend both the regression contract and the production-container smoke test when an adapter is enabled. No physical viewer, lens, filter, print, or hardware dimensions are inferred from model output.
